- `reviewAfter` is an optional ISO date on a reviewed playbook rule recording when its cited evidence must be re-reviewed; once that date passes, the evidence is stale even if the rule text still looks plausible.
- It applies to any rule that sets the field, and every `validateRules` run (the `check-rules.mjs` CLI and `tests/rules.spec.ts`) requires the date to parse and to stay strictly in the future.
- Failure mode: letting a rule live past its review date (or omitting the field so no date exists) keeps evidence nobody rechecked in force; the validator only rejects the whole document after the fact, with `rules[i].reviewAfter is overdue`, instead of renewing the rule.
- Reviewer check: inspect the rules' `reviewAfter` values (optional, but a rule without one has no review deadline), then run `node tools/memory/check-rules.mjs`; it prints `rules valid: N rule(s), M evidence case(s)` on success and fails on `rules[i].reviewAfter is overdue` or `rules[i].reviewAfter must be an ISO date`, and `tests/rules.spec.ts` ("rejects an expired rule and an overdue review") covers the rejection.
- Source: `tools/memory/rules.mjs`, `validateRules` date loop (`reviewAfter`/`expiresAt` `Date.parse` plus `time <= Date.now()` checks); `tools/memory/rules.json` rule `edit-read-first` sets `reviewAfter` to `2026-12-09T00:00:00.000Z`.

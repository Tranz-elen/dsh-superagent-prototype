- The rules evidence gate is `validateRules` in `tools/memory/rules.mjs`: a rule must list at least three distinct case ids in `evidence`, and when `knownCases` is supplied every id must exist in `cases.jsonl`; the same validator also requires a reviewable rule body, `check`, `confidence` and `scope.roles` before any rule reaches a prompt.
- A rule passes when `validateRules(document, { knownCases })` returns no errors: at least three distinct known case ids plus a valid rule body, `check`, `confidence` (`high`/`medium`), at least one `scope.roles` role, and, when present, ISO `reviewAfter`/`expiresAt` dates that are neither in the past nor overdue.
- Failure mode: without enough evidence a rule distilled from one or two vivid tickets is a guess with a version number, and if the gate is skipped or its minimum lowered it reaches the worker playbook unearned; the validator checks id count and membership, not that the cited cases actually support the rule.
- Reviewer check: run `node tools/memory/check-rules.mjs --rules tools/memory/rules.json --cases <stateDir>/cases.jsonl`; a passing file prints `rules valid: N rule(s), M evidence case(s)` and exits 0, while short, duplicate or unknown ids fail with `rules[i].evidence needs at least 3 case ids`, `rules[i].evidence has duplicate ids` or `rules[i].evidence references an unknown case`.
- Source: `tools/memory/rules.mjs`, `validateRules` (evidence length, duplicate and known-case checks; rule-text check via `validatePlaybookText` in `failure-candidates.mjs`); `evidence`, `check` and `scope` fields in `tools/memory/rules.json`; CLI `tools/memory/check-rules.mjs`.

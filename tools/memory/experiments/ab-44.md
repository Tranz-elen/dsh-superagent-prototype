- The candidate evidence count is the `cases` array of distinct case ids behind a failure candidate — not the `count` field, which counts every non-quarantined failure occurrence sharing that `signature`, so `count` can exceed `cases.length` when one ticket repeats a failure.
- It applies while `buildFailureCandidates` groups a corpus's `trace.failures` by signature: a signature is emitted only when `count >= FAILURE_MIN_CASES` (2), each counted failure adds its ticket's `c.id` to a per-signature `Set`, and the mapped candidate carries `cases: [...entry.cases]`.
- Failure mode: counting non-evidence cases — repeated identical failures in one ticket raise `count` without adding evidence cases, so reading `count` as the evidence count backs a candidate that has only one distinct case (and counting before the quarantine or missing-signature skip would cite failures that are not evidence at all).
- Reviewer check: check the evidence array builder — in `buildFailureCandidates` confirm `entry.cases` is a `Set` of `c.id` added only after the quarantine/ability-verdict and signature skips and mapped as `cases: [...entry.cases]`, then call `validateFailureCandidate`, which must reject a candidate whose `cases.length < 2` even when `count >= 2`.
